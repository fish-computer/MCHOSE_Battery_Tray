# MCHOSE 私有 HID 协议笔记

这份文档记录 **迈从（MCHOSE）2.4G 接收器的电量读取协议**是怎么摸出来的，
以及实测确认的帧格式。写下来主要是给后来的人省时间 —— 网上能搜到的
MCHOSE 协议资料，基本都只覆盖鼠标那一支（`0x11/0x12/0x13` + XOR `0xFF` 的一套），
键盘这一支和它对不上。

## 1. 设备与接口

接收器：

```
VID 0x41E4   PID 0x2001
Product      "MCHOSE 2.4G Wireless"
Manufacturer "Compx"
```

它在一个复合设备上暴露了多个 HID 接口，和我们有关的只有两个：

| 用途 | Usage Page | Usage | 报文长度 |
| --- | --- | --- | --- |
| 设置通道（本次没用到） | `0xFF04` | `0x0002` | 8 字节 FEATURE（report ID `0x06`） |
| **电量通道** | `0xFF02` | `0x0002` | 输入 20 / 输出 20（report ID `0x13`） |

设备路径长这样：

```
\\?\hid#vid_41e4&pid_2001&mi_01&col01#...#{4d1e55b2-f16f-11cf-88cb-001111000030}
```

打开时要用 `GENERIC_READ | GENERIC_WRITE` + `FILE_SHARE_READ | FILE_SHARE_WRITE`，
并且**同一个句柄既能读也能写**（用两个句柄分别读写也可以）。

> 顶层的键盘集合（`usagePage=0x0001, usage=0x0006`）会被键盘类驱动独占，
> `CreateFile` 返回 `ERROR_ACCESS_DENIED`。不要去碰它。

## 2. 帧格式

20 字节定长，第 0 字节是 report ID：

```
偏移   0      1      2      3 .. 18            19
     [0x13] [cmd] [param] [payload ...]      [checksum]
```

- `0x13`：固定 report ID
- `cmd` / `param`：命令与参数
- `payload`：命令参数或返回数据，用 `0x00` 补齐
- `checksum`：**所有前 19 字节的算术和 `& 0xFF`**（不是 XOR，不是 CRC）

校验例子（都是实机抓到的帧）：

```
13 4A 01 00 02 64 01 00 00 00 00 00 00 00 00 00 00 00 00  C5
   19+74+1+0+2+100+1 = 197 = 0xC5                            ✓

13 0A 01 00 04 05 64 01 00 00 00 00 00 00 00 00 00 00 00 8C
   19+10+1+0+4+5+100+1 = 140 = 0x8C                           ✓
```

## 3. 命令

| 帧 | 含义 | 说明 |
| --- | --- | --- |
| `13 05 01` | 建立会话 / 唤醒通道 | 打开句柄后先发它 |
| `13 4A 01` | **查询电量** | 有应答，见下 |
| `13 0A 01 00 04 05 <pct> <flags>` | 电量**主动推送** | 设备侧发起，不用请求 |

### 查询应答

```
13 4A 01 00 02 <pct> <flags> 00 ... 00 <sum>
               ^^^   ^^^^^^^
          固定 0x02   百分比 0..100
```

实测：`13 4A 01 00 02 64 01 ...` → `0x64 = 100%`，`flags = 0x01`。

### 主动推送

```
13 0A 01 00 04 05 <pct> <flags> 00 ... 00 <sum>
                  ^^^   ^^^^^^^
             固定 0x05   百分比 0..100
```

实测：`13 0A 01 00 04 05 64 01 ...` → 同样是 `100%`。

**百分比的偏移在原生命令里不一样**（应答在 `[5]`，推送在 `[6]`），
所以解析时要按 `cmd` 分支，不要只认一个下标。

### flags 位

| 位 | 含义 |
| --- | --- |
| `0x10` | 充电中 |
| `0x01` | 电池供电（未充电） |

## 4. 行为特征（踩坑记录）

- **推送是被动的**：打开句柄后，如果键盘是醒着的，大约 1 秒内就会自己送来一帧
  `13 0A ...`。主动发查询也能拿到应答，但**没有任何命令能让睡着的键盘说话**。
- **键盘睡着时通道完全静默**：实测空闲 8 秒 / 45 秒都收不到任何报文，
  `ReadFile` 一直超时。所以轮询没有意义，只会白白吵醒键盘 —— 本程序的策略是
  成功读取后 5 分钟才查一次、失败 15 秒重试、并在「用户刚有输入」的瞬间补一次。
- **`0xFF04` 的 `0x06` FEATURE 报告不是电量**：它恒为 `06 00 02 64 64 64 B5 4A`，
  里面的 `0x64` 只是常量 100，不是电量。别被它骗了（我们被骗过一轮）。
- **`0xFF02` 拿不到 report descriptor**：`HidD_GetReportDescriptor` 返回
  `ERROR_INVALID_FUNCTION` / 拒绝访问，只能靠 `HidP_GetCaps` + 实测。

## 5. 和其他 MCHOSE 协议的关系

网上能搜到的 MCHOSE 资料（比如 `Mchose-cli` 一类的项目）描述的是**鼠标**那一支：
report `0x11/0x12/0x13`、payload 整体 XOR `0xFF`、电量来自 `0xE2` 事件帧。

键盘这一支**不是 XOR，也不是那个帧格式** —— 它是上面这套「算术和校验 + `cmd/param`」。
所以别照抄鼠标的实现，会一直解不出数。

## 6. 怎么验证一个未知的迈从设备

1. `MchoseTray.exe --probe` 打全部 HID 集合，找 `usagePage=0xFF02`、输入长度 20 的那个；
2. 打开它，先发 `13 05 01`，再发 `13 4A 01`；
3. 收 20 字节报文，验校验和；
4. 按下表取百分比：`cmd==0x4A → [5]`、`cmd==0x0A → [6]`；
5. 拿官方驱动显示的百分比对一眼，对得上就通了。

如果你是别的型号，把 `--probe` 的输出和抓到的帧贴到 issue 里，适配起来通常只是
在 `protocol_mchose.cpp` 里加一个 `matches()` 分支。
